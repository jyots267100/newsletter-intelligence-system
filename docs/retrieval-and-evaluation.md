# Retrieval & Evaluation Methodology

## Why hybrid retrieval instead of semantic search alone

Semantic (embedding) search is good at matching *meaning* - a question
like "what's the new product?" can match a chunk that says "we're
launching DataSync Pro" even without shared words. It is comparatively
weak at matching *exact* terms: specific product names, acronyms, prices,
and dates can get buried if the surrounding phrasing differs from the
query. BM25 (keyword/lexical search) is the opposite: it is excellent at
exact-term matching and weak at paraphrase. Newsletters are full of both
kinds of information - narrative trends (good for embeddings) and concrete
facts like "$4.2 million" or "November 15, 2026" (good for BM25) - so
relying on only one retriever leaves a real gap. Hybrid retrieval, fusing
both rankings, covers both cases without having to pick one.

## Reciprocal Rank Fusion (RRF)

Each retriever (vector, BM25) returns its own ranked list of candidate
chunk IDs. RRF combines them with:

```
score(chunk) = sum over each list it appears in of  1 / (k + rank_in_that_list)
```

with `k = 60` (the value used in the original RRF paper, Cormack, Clarke &
Buettcher, 2009 - see `app/retrieval/fusion.py`). This avoids the need to
normalize or compare BM25 scores (unbounded, corpus-dependent) against
cosine distances (bounded, differently scaled) - RRF only cares about
*rank*, not raw score magnitude, which makes it simple, robust, and easy
to reason about. A chunk that both retrievers rank highly rises to the
top; a chunk only one retriever finds still gets a chance to surface.

## Why not a neural reranker

A cross-encoder reranker (e.g., scoring each (query, chunk) pair with a
second model) can improve precision further, but it adds latency, a
second model to load/maintain, and real engineering complexity. The
project brief is explicit that a reranker should only be added if
evaluation proves it's needed. At the scale this system targets (short
newsletters, a handful of pages), RRF over two complementary retrievers
already gives strong Recall@k (see results below) - there was no evidence
in evaluation that precision was the bottleneck, so a reranker was not
added.

## Evaluation dataset

`data/sample/eval_dataset.json` contains 7 hand-written questions against
a synthetic, fully-fictional sample newsletter
(`data/sample/sample_newsletter.pdf`, generated by
`scripts/generate_sample_newsletter.py`). Each question has a
hand-labeled `expected_page` (the page that actually contains the answer)
and a short list of `expected_answer_facts` (strings that should appear in
a correct answer).

This is intentionally small and hand-labeled rather than large and
automatically generated - at this project's scale, a small trustworthy
set beats a large noisy one, and it keeps the evaluation fully
inspectable (you can read all 7 questions and judge for yourself whether
they're fair).

## Metrics

Run with:

```bash
python scripts/generate_sample_newsletter.py   # once
python scripts/evaluate_retrieval.py           # retrieval-only, no API calls
python scripts/evaluate_retrieval.py --with-llm  # also scores Gemini answers (uses API quota)
```

- **Retrieval Recall@k** - fraction of questions where the expected page
  appears anywhere in the top-k retrieved chunks. This measures whether
  the hybrid retriever *could* have supported a correct, grounded answer.
- **Retrieval MRR (Mean Reciprocal Rank)** - rewards the expected page
  appearing *earlier* in the ranked list, not just somewhere in top-k.
- **LLM answer fact hit rate** (`--with-llm` only) - fraction of questions
  where at least one `expected_answer_facts` string appears in Gemini's
  generated answer. This is a coarse, keyword-based groundedness proxy,
  not a rigorous entailment check - it catches obvious failures (e.g. the
  model declining to answer, or answering a different question) without
  needing a second LLM-as-judge call.
- **LLM citation correctness** (`--with-llm` only) - fraction of questions
  where the citation returned alongside the chat answer points to the
  correct expected page.

### Actual measured results

Measured by running the exact commands above against this repository's
code, with `EMBEDDING_MODEL=sentence-transformers/all-MiniLM-L6-v2` (the
default) and a freshly generated `sample_newsletter.pdf`:

```
$ python scripts/generate_sample_newsletter.py
$ python scripts/evaluate_retrieval.py

--- Summary ---
Questions evaluated:        7
Retrieval Recall@5:         100.00%
Retrieval MRR:              1.000
```

The hybrid retriever put the correct page in rank 1 for all 7 questions
(hence MRR of exactly 1.0). This is a clean, honest result for what it
is - and it's worth being direct about what it does and doesn't prove.
The sample newsletter is short (4 pages), each page covers a clearly
distinct topic (announcement / stats / risks / actions), and the
questions were written to be unambiguous. That combination makes this an
*easy* retrieval problem by design, not evidence that hybrid retrieval is
flawless. A noisier, longer, or more repetitive real document would be a
harder and more realistic test; re-run the script against your own
documents and dataset to get numbers that reflect your actual use case.
`--with-llm` was not run for this README (it spends real Gemini quota) -
run it yourself with `GEMINI_API_KEY` set to also measure answer-fact
hit rate and citation correctness end to end.

## What this evaluation does and doesn't prove

It proves the retrieval layer can find the right page for a set of
realistic, varied question types (announcements, statistics, risks,
action items with owner/deadline) against a multi-page document, and
(optionally) that end-to-end answers are grounded in that retrieval. It
does **not** prove retrieval quality at scale (tested on one short
document), does not measure latency/cost under load, and does not
replace manual review of analysis output quality - see `docs/interview-
guide.md` for what a production evaluation setup would add.
